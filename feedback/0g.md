# 0G Compute integration feedback (Nautica, ETHGlobal)

Use case: every citizen-science photo is classified by `qwen3-vl-30b` running in a
TEE via the 0G Router, and we store an honest attestation. `simulated:false` is set
only when the TEE was genuinely verified. Notes from wiring it end to end.

## What worked well

- **Router path is excellent.** `POST https://router-api.0g.ai/v1/chat/completions`,
  OpenAI-compatible, a static `sk-` key, no wallet key on the server. The multimodal
  request (base64 `image_url`) just worked with `qwen3-vl-30b`.
- **`verify_tee: true` + `X-0G-Provider-Trust-Mode: verified`** is a great primitive:
  the Router validates the provider's TEE signature and returns
  `x_0g_trace.tee_verified`. Real call: crab photo -> correct label, `tee_verified:
  true`. Omitting `verify_tee` -> `tee_verified` absent. Clean positive/negative.
- **`GET /v1/models` needs no auth** and exposes `verifiability` / `tee_type` /
  `tee_verifier` per model, so we read real metadata instead of hardcoding.
- **Cheap.** Billing came back ~1.4e-5 OG per verification (~$0.000003). The account
  was preloaded with 0.1 OG, enough for thousands of calls. Funding UX at pc.0g.ai
  was smooth (deposit -> create key with a trust mode -> done).

## Rough edges / doc gaps

1. **`/proxy/signature` self-verify does NOT work on the router path.** The docs
   describe `GET {providerUrl}/v1/proxy/signature/{chatId}` to fetch the raw
   signature and verify EIP-191 yourself. For **router-routed** chats this always
   returns `400 {"error":"...chat id not found or expired, chat_id_not_found"}` — the
   provider doesn't have the router's `ZG-Res-Key` chat id (nor the body `id`). The
   router also does not proxy the signature (`/v1/proxy/signature/...` on the router
   base is 404). So independent EIP-191 self-verification is only reachable via the
   **direct broker** path (funded `ethers.Wallet`, single-use headers). This cost the
   most time. Please either (a) document that `/proxy/signature` is direct-broker
   only, or (b) let the router proxy it for router chats.
2. **Mainnet Compute contract addresses aren't in the docs.** The mainnet
   contract-addresses page lists only Storage. We needed the inference **Serving**
   contract for on-chain provenance and found it only in the SDK
   (`0g-compute-ts-sdk/src.ts/sdk/constants.ts`, `CONTRACT_ADDRESSES.mainnet`):
   - Ledger: `0x2dE54c845Cd948B72D2e32e39586fe89607074E3`
   - **Inference Serving: `0x47340d900bdFec2BD393c626E12ea0656F938d84`**
   - FineTuning: `0x4e3474095518883744ddf135b7E0A23301c7F9c0`
   Please list these on the mainnet page.
3. **SDK drift.** `@0glabs/0g-serving-broker` is deprecated (renamed
   `@0gfoundation/0g-compute-ts-sdk`) and ships **testnet** addresses; its inference
   `Service` struct also changed (the current one adds `teeSignerAddress` +
   `teeSignerAcknowledged`, the older one had neither). Reverse-engineering the ABI
   from the deprecated package sent us down a wrong path first.
4. **`x_0g_trace` and `ZG-Res-Key` are under-documented.** The response trace
   (`tee_verified`, `provider`, `request_id`, `billing`) and the chat-id header
   weren't in an obvious place; we probed to find them.
5. **`tee_verified` is three-state.** `true` / `false` / absent (when `verify_tee`
   omitted) each mean different things; the `false` vs absent distinction is
   security-relevant and worth spelling out.
6. **`qwen3-vl-30b` is mainnet-only.** Absent from the testnet router (which serves
   `qwen2.5-omni` / `qwen-image-edit`), so there's no free path to demo the strong
   vision model. Fine given the cost, but worth noting for hackathon teams.

## What we shipped

- Tier A: router-attested `verify_tee`, `simulated` derived in one place, XP awarded
  only on a genuinely verified pass (kill-test enforces `simulated:false` IFF
  `tee_verified===true`).
- On-chain provenance: read the serving provider's Serving record (registered
  `teeSignerAddress`, `verifiability`, acknowledgement) and attach it to the
  attestation. Real, independently checkable data even though full EIP-191
  self-verify needs the direct-broker path.

## Suggestions

- Document that `/proxy/signature` is direct-broker only (or proxy via the router).
- List mainnet Compute (Serving/Ledger) addresses in the docs.
- Document `x_0g_trace` / `ZG-Res-Key` / the three-state `tee_verified` in the
  verifiable-execution page.
