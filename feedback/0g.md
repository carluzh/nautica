# 0G Compute integration feedback (Nautica, ETHGlobal)

Our use case: every citizen-science wildlife photo is classified by `qwen3-vl-30b`
running in a 0G TEE, and we store an attestation where `simulated:false` is set only
on a genuinely verified inference. We took the integration deep: the Router path,
on-chain provenance from the Serving registry, and independent Intel TDX quote
verification. These notes are from a full, test-driven integration (every claim
below was checked against the live mainnet endpoints).

## What worked really well

- **The Router is excellent.** `POST https://router-api.0g.ai/v1/chat/completions`,
  OpenAI-compatible, a single static `sk-` key, no wallet on the server. Multimodal
  (`image_url` base64) just worked with `qwen3-vl-30b`.
- **`verify_tee: true` + `X-0G-Provider-Trust-Mode: verified`** is a great primitive:
  the Router validates the provider's TEE signature and returns
  `x_0g_trace.tee_verified`. We proved it both ways (present -> `true`, omitted ->
  absent).
- **`GET /v1/models`** (no auth) exposes `verifiability`/`tee_type`/`tee_verifier`,
  so we read real metadata instead of hardcoding.
- **`response_format:{type:"json_object"}` + `seed`** work, are deterministic, and do
  not break `verify_tee` (still 200, `tee_verified:true`). Nice for structured tasks.
- **`GET {providerUrl}/v1/quote` is the standout.** It returns a real 5006-byte Intel
  TDX v4 quote (plus `event_log`/`vm_config`/`tcb_info`), publicly, no auth, and its
  `report_data` decodes to the provider's on-chain `teeSignerAddress`. This is the
  most powerful and least-advertised verification surface you have (see below).
- **Cheap.** Billing was ~1.4e-5 OG per verification (~$0.000003); a preloaded 0.1 OG
  account covers thousands of calls. Funding at pc.0g.ai was smooth.

## The verification model - the single most important feedback

There are **three distinct verification layers**, and the docs blur them:

1. **Router `verify_tee`** - the Router checks the provider's TEE signature and
   returns `tee_verified`. Convenient, but you are trusting the Router to have checked.
2. **On-chain Serving registry** (`getService(provider)` on the inference Serving
   contract) - the provider's registered `teeSignerAddress`, `verifiability`, and
   `teeSignerAcknowledged`. Public, independent.
3. **The provider's Intel TDX quote** (`GET /v1/quote`) - a real DCAP quote whose
   `report_data` binds to the on-chain signer, verifiable against Intel's root of
   trust (Automata on-chain, Phala off-chain, or `dcap-qvl` locally). The deepest,
   and it is public + independent.

**The honesty nuance you must document:** the current mainnet providers we hit
(e.g. the `qwen3-vl-30b` provider `0x4415ef5C…`) advertise a `verifiability` mode but
are `ProviderType: centralized` with `TargetSeparated: true`, and
`GET /v1/proxy/attestation/report` returns **501 "forwards to an upstream API without
local TEE attestation."** In other words the **model** runs on a centralized upstream
(aliyun-hosted qwen) and only the **broker proxy** runs inside the TDX enclave. So
`verify_tee`, the response signature, and the TDX quote all attest that a
**TEE-resident broker signed this response** - they do **not** prove the model weights
executed in a TEE. That is a real gap between the "verifiable AI inference in a TEE"
positioning and today's reality (a TEE-attested broker in front of a centralized
model). It does not make the verification worthless (the broker signing is genuine and
independently checkable), but builders can only honestly claim "independently verified
the provider's TEE attestation," not "the model ran in a TEE." **Please make this
explicit in the docs and, ideally, in the on-chain `verifiability` field.**

## Rough edges / doc gaps (each verified live)

1. **`/proxy/signature` is direct-broker only.** The docs describe
   `GET {providerUrl}/v1/proxy/signature/{chatId}` to fetch the raw signature and
   self-verify EIP-191. On the **Router** path this always returns
   `400 {"error":"…chat id not found or expired, chat_id_not_found"}` (the provider
   never sees the Router's `ZG-Res-Key` chat id), and the Router does not proxy the
   signature (`/v1/proxy/signature/…` on the router base is 404). So independent
   per-response signature self-verify requires the **direct broker** path (funded
   `ethers.Wallet` + `getRequestHeaders` + `processResponse`). This cost us the most
   time. Please either document that `/proxy/signature` is direct-broker only, or let
   the Router proxy it / expose a Router verify endpoint.

2. **Mainnet Compute contract addresses are not in the docs.** The mainnet
   contract-addresses page lists only Storage. We found the Compute addresses only in
   the SDK (`0g-compute-ts-sdk/src.ts/sdk/constants.ts`, `CONTRACT_ADDRESSES.mainnet`):
   - Ledger: `0x2dE54c845Cd948B72D2e32e39586fe89607074E3`
   - **Inference Serving: `0x47340d900bdFec2BD393c626E12ea0656F938d84`**
   - FineTuning: `0x4e3474095518883744ddf135b7E0A23301c7F9c0`
   Please list them on the mainnet page.

3. **SDK drift.** `@0glabs/0g-serving-broker` is deprecated (renamed
   `@0gfoundation/0g-compute-ts-sdk`), ships **testnet** addresses, and its inference
   `Service` struct changed (the old one has no signer; the current one adds
   `teeSignerAddress` + `teeSignerAcknowledged`). Reverse-engineering the deprecated
   package's ABI sent us down a wrong path first (we probed a testnet address on
   mainnet and got empty returns).

4. **The referenced Automata DCAP mainnet is dead.** `redpill-verifier` points at
   `rpc.ata.network` (chainId 65536, `0xE26E11B2…`), which now returns
   `-32002 "Automata Attestation L2 is retired."` for every call. Builders need a
   **live** DCAP verifier - Ethereum Sepolia's Automata deployment
   (`0x76A3657F2d6c5C66733e9b69ACaDadCd0B68788b`) works today (free `eth_call`), but a
   current ETH/Base **mainnet** Automata address should be documented for production.

5. **On-chain DCAP verify can revert on missing PCCS collateral.** The aliyun
   platform's FMSPC collateral happened to be present on Sepolia (so
   `verifyAndAttestOnChain` returned `isValid:true`), but this is not guaranteed per
   provider/network. The off-chain path (Phala / `dcap-qvl`) fetches collateral itself
   and sidesteps this - worth calling out.

6. **`x_0g_trace` / `ZG-Res-Key` / three-state `tee_verified` are under-documented.**
   The response trace (`tee_verified`, `provider`, `request_id`, `billing`) and the
   chat-id header are not in an obvious place, and `tee_verified` is three-state
   (`true` / `false` / absent when `verify_tee` is omitted); the false-vs-absent
   distinction is security-relevant and should be spelled out.

7. **Model-catalog vs provider-registry `verifiability` disagree.** `/v1/models`
   reports `qwen3-vl-30b` as `TeeTLS`, but the serving providers register (`getService`)
   as `TeeML`. That inconsistency makes the trust-mode routing hard to reason about
   (`verified` = TeeML+TeeTLS, `private` = TeeML only); we used `verified` to be safe,
   but the mismatch should be reconciled.

8. **The two funding models are very different and easy to confuse.** The Router path
   needs only a prepaid `sk-` credit (ours: ~0.1 OG). The direct-broker path needs a
   funded wallet with a per-provider sub-account (`MIN_LOCKED_BALANCE` = 1 OG,
   `acknowledgeProviderSigner` min transfer 1 OG) plus gas - a ~0.1 OG account is below
   the direct-path floor. Document the split clearly.

9. **`qwen3-vl-30b` is mainnet-only** (absent from the testnet router, which serves
   `qwen2.5-omni` / `qwen-image-edit`), so there is no free path to demo the strong
   vision model. Fine given the cost, but worth noting for hackathon teams.

## What we shipped (as an honest reference implementation)

- **Router `verify_tee`** with `simulated` derived in exactly one place
  (`!(x_0g_trace.tee_verified === true)`), kill-tested so `simulated:false` cannot be
  set without a genuine verdict; XP is awarded only on a verified pass.
- **On-chain provenance**: `getService(provider)` -> registered `teeSigner`,
  `verifiability`, acknowledgement, attached to the attestation.
- **Independent Intel TDX quote verification**: `GET /v1/quote` -> assert
  `report_data == on-chain teeSigner` -> verify the quote (Automata on-chain primary,
  Phala off-chain fallback), stored as `quoteVerified` + `quoteVerifier`.
- We deliberately do **not** claim the model ran in a TEE; our UI copy says
  "independently verified the provider's Intel TDX attestation."

## Suggestions (summary)

- Make the **broker-vs-model TEE distinction explicit** (the centralized-upstream
  reality) in docs and the on-chain `verifiability` field.
- Document that `/proxy/signature` is **direct-broker only**, or proxy it via the
  Router.
- List **mainnet Compute contract addresses** and a **live DCAP verifier** address.
- Reconcile the **model-catalog vs provider-registry `verifiability`** mismatch.
- Surface the **public `/v1/quote` DCAP path** as a first-class independent-verification
  story - it is your strongest guarantee and it is already public.
